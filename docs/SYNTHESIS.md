## CONFLICTS
- PASTE vs KEYSTROKE-INJECTION — the biggest cross-section wording clash, but NOT a factual disagreement. Source (SpeechManager.pasteText, lines 1028-1057) shows the mechanism is BOTH: it clears NSPasteboard, setString's the text, THEN synthesizes Cmd+V (virtualKey 55 + 9) posted to .cghidEventTap. So it is literally a clipboard paste DELIVERED BY a synthetic keystroke. DISTRIBUTION and LICENSING correctly describe it as 'synthetic Cmd+V keystroke injection' (the technically precise framing that justifies why MAS sandbox is impossible). BRAND-COPY and LANDING-PAGE deliberately forbid 'types key-by-key' and mandate 'pastes / appears', and brand-copy explicitly flags the other drafts as 'wrong' for saying keystrokes. RESOLUTION: both are right at their altitude. User-facing copy MUST say 'appears / gets pasted at your cursor' (never 'types itself letter by letter' — text lands all-at-once in one paste, so char-by-char is a genuine factual error for marketing). Technical/distribution docs MUST keep 'synthetic Cmd+V keystroke injection to .cghidEventTap' because that exact mechanism is the load-bearing reason the app cannot be sandboxed. Do not let brand-copy's 'keystrokes is wrong' note bleed into the distribution rationale, and do not let distribution's 'keystroke injection' phrasing bleed into marketing copy. The one place this MUST be corrected: brand-copy/landing FAQ 'Why isn't this on the App Store?' currently says only 'Accessibility permission sandboxed apps can't request' — that is true but understates it; keep it simple for users but ensure the DISTRIBUTION doc (not user copy) carries the full multi-blocker technical reason.
- GRANDFATHERING EXISTING USERS — two sections give directly opposed instructions. DISTRIBUTION says 'Do NOT try to grandfather individual existing users with free keys... v1.3.0 stays free, v2.0 is $4.20, build it yourself or pay' and treats the version boundary as the only grandfather mechanism. LICENSING builds an explicit in-app grandfather heuristic (detectGrandfather() flags returning users as licensed-forever via persisted UserDefaults keys) as 'the single most important anti-riot line of code.' These are reconcilable and should BOTH ship: they operate at different layers. Distribution's point is 'do not issue free LICENSE KEYS to old users' (correct — there is no email list to verify against, and no way to prove who existed). Licensing's point is 'if the NEW v2 binary detects a prior install's real preferences on first run, mark it licensed locally, no nag' (correct — it is best-effort, costs nothing, and only affects someone who upgrades the same binary in place). SETTLE THIS: adopt licensing's local detectGrandfather() heuristic (it is honest, flagged as best-effort, and safe because it fails toward generosity) AND adopt distribution's rule of never minting free keys. The residual gap distribution correctly notes: a v1.3.0 user who never touched a setting won't trip the heuristic — that user simply keeps the still-free v1.3.0, or pays $4.20 for v2, which is acceptable.
- TRIAL MODEL — a real divergence to decide. LICENSING ships a full 14-day degrade-never-brick trial for NEW v2 installs with trial-clock UserDefaults keys (trialFirstRun/trialMaxDays) and a .trial/.expired state machine. DISTRIBUTION argues AGAINST any trial clock: 'The free/self-built build IS the trial... A time-limited trial on an app that was fully free yesterday reads as a takeaway... Do NOT re-impose any trial clock.' Both are defensible; they optimize for different things. Licensing's trial gates ONLY paid engines/clipboard-cycling/incremental (Apple Speech hold-to-talk never gated), so 'expiry' just falls back to the free-tier feature set — which is arguably not a takeaway at all. Distribution's cleaner story is 'there is no trial, the free build is the free tier, pay for the maintained one.' RECOMMENDATION TO RESOLVE: lean toward distribution's simpler no-trial framing for MESSAGING (never advertise a '14-day trial' — it muddies the 'always free' story), but licensing's degrade-never-brick gating code is harmless to ship as the enforcement floor since it only ever drops a NEW user to the free-tier engine. Decision needed from owner: do we surface a trial countdown in the menu (licensing's 'X days left' item) or not (distribution's stance)? They cannot both be true in the UI.
- LANDING PAGE vs SHIPPED-PRODUCT FEATURE SET — a timing/scope conflict, not a factual one. The LANDING-PAGE section deliberately built the page against the CURRENT v1.3.0 reality: it explicitly EXCLUDES any mention of Sparkle, notarization/'Gatekeeper clears', PolyForm license, or license keys/activation, and its App Store FAQ tells users to right-click-Open past the ad-hoc Gatekeeper warning. But DISTRIBUTION + LICENSING are shipping v2.0.0 WITH all of those (notarized so no Gatekeeper warning, Sparkle auto-update, PolyForm license, $4.20 license activation). So the built landing page describes the FREE v1.3.0, while the plan sells v2.0.0. RESOLUTION: the landing page must be REVISED for the v2 launch before it goes live — add the notarized/no-warning claim (now TRUE for v2), add Sparkle-based updates framing, add the $4.20 purchase/license flow, add the PolyForm 'build it yourself free' line, and REMOVE the 'right-click to open past Gatekeeper' instruction (v2 is notarized, that step is only for v1.3.0). The landing section's fabrication-avoidance was correct for v1.3.0 but those are no longer fabrications for v2. Do not ship the current page as-is for the paid launch.
- ASSET STORYBOARD vs LANDING-PAGE HERO ANIMATION — minor, worth flagging. The LANDING-PAGE hero animation renders text 'character-by-character type-out with blinking caret'. The ASSETS runbook explicitly corrects this: text lands ALL AT ONCE via a single clipboard Cmd+V paste (incrementalMode is false by default), and calls char-by-char storyboards 'wrong'. These don't strictly conflict (the landing hero is a stylized CSS animation, not a literal capture of app behavior, and a stylized type-out is a legitimate design choice), but for CONSISTENCY the real demo VIDEO/GIF must show the paste-all-at-once behavior (per assets), while the CSS hero can keep its stylized type-out only if it does not claim to be real footage. Ensure the video and the hero don't contradict each other on screen next to each other.
